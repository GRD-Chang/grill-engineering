# 飞书进度通知

飞书通知默认关闭。通过[个人运行配置](user-defaults.md#飞书进度通知)启用；接收人的 `open_id` 必须与 CLI profile 对应的应用一起核对，并保存该应用的 `app_id`。凭据由官方 `lark-cli` 管理。未启用时不会调用 CLI、启动发送线程或积压消息。

新 Run 保存接收人、profile、应用绑定与开关快照。修改个人默认仅影响新 Run；`run --no-notifications` 可关闭单次新任务。每次发送前核对 CLI 返回的应用与机器人身份；应用绑定变化会停止发送该请求，开发继续。需要恢复原 Run 的发送时，恢复原 profile 对应的应用与凭据；不支持为已有 Run 换收件人。

## 收到什么

每个事件是一条独立的 Card 2.0 compact 私聊消息：任务启动，开发／验收／发布 Agent 每轮启动与结果，子任务完成，最终 PR 创建，待批准，人工阻塞、恢复、停止或放弃，以及整体交付完成。同轮续接不重复启动，重复检查不会刷屏。发布说明已准备、子任务完成和整体交付完成分别表达。

卡片使用蓝色表示开始和进展，绿色表示通过和完成，橙色表示验收未通过后自动修复，黄色表示人工边界，红色表示执行故障。卡片保留明确文字、已有结果摘要与可信耗时；未知内容不会推测补齐。按钮仅打开真实 Issue 或 PR，不能执行批准或恢复。

Card 2.0 需要支持该格式的飞书客户端；本功能不降级为 Card 1.0。会话摘要与锁屏展示由客户端决定。窄屏单列布局使用飞书内置状态主题，长内容截断并提供本地查询命令。

## 发送记录与恢复

`agent-run status <run-id> --json` 与 `agent-run history <run-id> --json` 的 `notifications` 包含未送达原因与发送记录；普通输出提示不可用或未确认送达数量。两个查询始终只读，不触发发送。

Executor 管理发送线程；外部 CLI 在业务锁外执行。一次投递最多尝试三次，每次预检与发送共用十秒期限。退出时最多等待两秒排空，随后取消并回收子进程；独立短期监督进程也会在 Executor 死亡或期限到达时回收 CLI 后代。

确定未送达的消息保留待发状态，新业务事件或显式恢复会触发后续尝试。积压的过时进展合并为当前状态摘要，已经解除的阻塞不会作为当前待办补发。缺少送达凭据或中途断连时记为 `unknown`，保守地不自动重发该条；这避免跨越服务端短期幂等窗口后盲目重复发送，但不能承诺绝对不重不漏。

本地记录保存在 Run 状态目录的 `notifications/` 下：最多保留32条待发或结果未知记录和256条最近投递记录，以及当前有界 history 视图的去重身份。记录不是完整消息档案。没有通知常驻服务，也不会在退出后无限重试。

自动测试使用隔离 CLI 替身，验证发送请求、生命周期与资源回收，不访问真实账号或发送真实聊天消息。
