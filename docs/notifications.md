# 飞书进度通知

飞书通知默认关闭。首次接入见[安装与配置](install.md#飞书通知可选)，通过[个人运行配置](user-defaults.md#飞书进度通知)启用；接收人的 `open_id` 必须与 CLI profile 对应的应用一起核对，并保存该应用的 `app_id`。凭据由官方 `lark-cli` 管理。未启用时不会调用 CLI、启动发送线程或积压消息。

新 Run 保存接收人、profile、应用绑定、开关与模式快照。修改个人默认仅影响新 Run；`run --no-notifications` 可关闭单次新任务。每次发送前核对 CLI 返回的应用与机器人身份；应用绑定变化会停止发送该请求，开发继续。需要恢复原 Run 的发送时，恢复原 profile 对应的应用与凭据；不支持为已有 Run 换收件人。

## 语言与业务事实

通过 `agent-run settings configure --language zh` 或 `--language en` 选择新任务的语言；默认中文。卡片标题、角色、检查标签、按钮、耗时和程序操作指引使用 Run 创建时固定的语言。修改个人默认不会改变已创建任务或待发送卡片的语言。

原始 Issue 标题、Agent 摘要、Findings 和外部证据保持原文，允许与卡片界面语言不同；命令与机器字段不翻译。通知选择、失败分类、颜色、下一步和去重身份由既有结构化事实决定，修改 Status/History 的展示措辞不会增加通知或改变其语义。

## 收到什么

新任务启用后默认精简模式，按交付方式选择关键节点：

| 节点 | 有子任务 | 无子任务（Parent-only） |
| --- | --- | --- |
| 任务启动 | 一次 | 一次 |
| 子任务首次实际开发开始、完成 | 每个子任务各一次 | 不适用 |
| 整体验收开始、首次转入整体修复 | 各一次 | 不发送 |
| 正式验收通过 | 整体验收通过 | 完整需求验收通过 |
| 待批准、最终完成 | 分别发送 | 分别发送 |
| 人工恢复实际结果、人工待办及异常 | 保留 | 保留 |

子任务排队或被选中不表示已经开始；内部返工、Resume 和换线程不重复开始通知。整体修复按实际事实说明“将自动修复”或“正在自动修复”，后续修复和重验不逐轮发送。Parent-only 的内部验收开始和修复过程保持安静。

通过消息只依据当前有效的正式验收结论；局部修复通过、尚未提升的修复候选和缺少 Findings 都不能代替正式通过。验收通过与待批准各自触发、各自去重，即使紧接发生也分别保留，不等待合并消息。验收通过不表示 PR 已创建、检查完成、已合并或收尾完成。

精简不单独发送 PR 创建、发布说明准备或每轮 Agent 启停。详细模式保留过程粒度，但同一事实不会同时发送关键节点和重复的过程消息；同次观察到 PR 已创建且可批准时只发批准消息，检查仍在等待时可单独通知 PR 创建。人工待办、故障、预算暂停、停止、放弃及合并后待清理仍保留。

人工 `resume` 反馈实际推进结果：Agent 真正开始工作，或 Controller 实际继续检查、合并、收尾；失败或立即出现人工待办时按真实结果提示。收到请求或命令退出 0 不等于恢复成功，不能证明开始时不宣称成功。任务本来已在运行时只提示终端；同次恢复失败与对应故障去重。自动 Agent 续接和通知发送恢复不属于人工 Resume。无法定位有效 Run 或收件配置的错误仍沿用 CLI 错误边界。

每条消息使用 Card 2.0 compact 私聊卡片。同轮续接不重复启动，重复检查不会刷屏。发布说明已准备、子任务完成和整体交付完成分别表达。

卡片使用蓝色表示开始和进展，绿色表示通过和完成，橙色表示验收未通过后自动修复，黄色表示人工边界，红色表示执行故障。卡片保留明确文字、已有结果摘要与可信耗时；没有摘要或可靠耗时直接省略。Agent 结束显示含同轮续接的本轮执行耗时；子任务完成显示子任务累计 Agent 执行耗时；人工待办和最终结果区分累计执行耗时与包含等待的任务历时。补发按业务事件计时，不增加投递等待。按钮仅打开真实 Issue 或 PR，不能执行批准或恢复。

子任务完成表示已经完成并进入集成成果，不是开发或验收 Agent 刚结束。完成卡片保留真实标题、总体进度和下一步，并分别汇总开发（含各类修复）与验收投入：

- 轮数按 Semantic Agent Attempt 身份去重；同轮 Resume、Output Repair、换 Thread 不增加轮数，预算窗口 ordinal 重置也不丢失历史轮数。
- 执行耗时来自关联 Invocation 的实际执行段，包含同轮续接，不计暂停、人工或 CI 等待。原有累计 Agent 执行耗时仍包含 Publication，不能用开发加验收替代全部总计或任务历时。
- 模型与推理强度来自实际 Invocation 的 Thread Binding。一致时简洁显示，变化时按组合展示参与轮数与执行耗时；同轮参与多个组合时明确提示各组轮数不可相加。
- 历史或关联缺失、计时不完整时省略无法证明的累计字段，保留独立可靠信息；未知值不补零，不用当前默认或最后配置猜测。

只统计 Controller 可识别的顶层开发与验收，不推断内部 subagent、Token 或费用。卡片不逐轮列时间表，也不调用模型生成额外摘要；使用卡片中的 `agent-run history <run-id> --details` 查看逐轮配置、耗时及证据。统计复用既有 History，不另存一套累计历史。

Card 2.0 需要支持该格式的飞书客户端；本功能不降级为 Card 1.0。会话摘要与锁屏展示由客户端决定。窄屏单列布局使用飞书内置状态主题，长内容截断并提供本地查询命令。

## 发送记录与恢复

`agent-run status <run-id> --json` 与 `agent-run history <run-id> --json` 的 `notifications` 包含未送达原因与发送记录；普通输出提示不可用或未确认送达数量。两个查询始终只读，不触发发送。

Executor 管理发送线程；外部 CLI 在业务锁外执行。一次投递最多尝试三次，每次预检与发送共用十秒期限。退出时最多等待两秒排空，随后取消并回收子进程；独立短期监督进程也会在 Executor 死亡或期限到达时回收 CLI 后代。

确定未送达的消息保留待发状态，新业务事件或显式恢复会触发后续尝试。恢复时只发送模式允许的最新有效业务状态，允许遗漏过时进展，已经解除的阻塞不会作为当前待办补发。缺少送达凭据或中途断连时记为 `unknown`，保守地不自动重发该条；这避免跨越服务端短期幂等窗口后盲目重复发送，但不能承诺绝对不重不漏。

本地记录保存在 Run 状态目录的 `notifications/` 下：最多保留32条待发或结果未知记录和256条最近投递记录，以及当前有界 history 视图的去重身份。首次节点身份按固定子任务集合保存，人工恢复结果另保留至多256个去重身份；历史裁剪不会使已通知的首次开始重新发送。记录不是完整消息档案。新版 Runner 对已有任务也统一执行上述节点选择规则，不保留旧通知策略或逐条补发历史进展。没有通知常驻服务，也不会在退出后无限重试。

自动测试使用隔离 CLI 替身，验证发送请求、生命周期与资源回收，不访问真实账号或发送真实聊天消息。
