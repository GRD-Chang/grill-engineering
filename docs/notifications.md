# 飞书进度通知

飞书通知默认关闭。首次接入见[安装与配置](install.md#飞书通知可选)，通过[个人运行配置](user-defaults.md#飞书进度通知)启用；接收人的 `open_id` 必须与 CLI profile 对应的应用一起核对，并保存该应用的 `app_id`。凭据由官方 `lark-cli` 管理。未启用时不会调用 CLI、启动发送线程或积压消息。

新 Run 保存接收人、profile、应用绑定、开关与模式快照。修改个人默认仅影响新 Run；`run --no-notifications` 可关闭单次新任务。每次发送前核对 CLI 返回的应用与机器人身份；应用绑定变化会停止发送该请求，开发继续。需要恢复原 Run 的发送时，恢复原 profile 对应的应用与凭据；不支持为已有 Run 换收件人。

## 语言与业务事实

通过 `agent-run settings configure --language zh` 或 `--language en` 选择新任务的语言；默认中文。卡片标题、角色、检查标签、按钮、耗时和程序操作指引使用 Run 创建时固定的语言。修改个人默认不会改变已创建任务或待发送卡片的语言。

原始 Issue 标题、Agent 摘要、Findings 和外部证据保持原文，允许与卡片界面语言不同；命令与机器字段不翻译。通知选择、失败分类、颜色、下一步和去重身份由既有结构化事实决定，修改 Status/History 的展示措辞不会增加通知或改变其语义。

## 收到什么

新任务启用后默认精简模式，按交付方式选择关键节点：

| 节点 | 有子任务 | 无子任务（Parent-only） |
| --- | --- | --- |
| 任务创建 | 一次 | 一次 |
| 完整需求首次实际开发开始 | 不适用 | 一次 |
| 子任务首次实际开发开始、完成 | 每个子任务各一次 | 不适用 |
| 整体验收开始、首次转入整体修复 | 各一次 | 不发送 |
| 正式验收通过 | 整体验收通过 | 完整需求验收通过 |
| 待批准、最终完成 | 分别发送 | 分别发送 |
| 人工恢复实际结果、人工待办及异常 | 保留 | 保留 |

任务创建、排队、准备调用或接受 Resume 请求均不表示 Agent 已开始；完整需求与子任务均以 Invocation 的实际线程启动事实触发首次开发通知。内部返工、Resume 和换线程不重复开始通知。整体修复按实际事实说明“将自动修复”或“正在自动修复”，后续修复和重验不逐轮发送。Parent-only 的内部验收开始和修复过程保持安静。

通过消息只依据当前有效的正式验收结论；局部修复通过、尚未提升的修复候选和缺少 Findings 都不能代替正式通过。验收通过与待批准各自触发、各自去重，即使紧接发生也分别保留，不等待合并消息。验收通过不表示 PR 已创建、检查完成、已合并或收尾完成。

精简不单独发送 PR 创建、发布说明准备或每轮 Agent 启停。详细模式保留过程粒度，但同一事实不会同时发送关键节点和重复的过程消息；同次观察到 PR 已创建且可批准时只发批准消息，检查仍在等待时可单独通知 PR 创建。人工待办、故障、预算暂停、停止、放弃及合并后待清理仍保留。

两种模式均逐对象通知全部 Ticket、Parent-only、Run Acceptance/Repair、Run Publication 及独立 Run 级人工待办，不依赖当前选中的 Ticket 或顶层状态。每个待办说明对象、适用 Generation、原始原因、影响范围和恢复动作。局部 Human Blocker、执行失败、预算耗尽、监督超时、主动暂停或发布待办只影响该 Ticket 及依赖工作；独立工作继续。全局停止与局部待办可以同时存在，先解除全局边界也不会隐式解除局部门禁。局部恢复命令明确携带 `--ticket N`。

status/history 的 `operator_actions` 与卡片共用只读事实；正常依赖等待、排队、CI 运行和自动更新期间已失效的旧批准不属于待办。同一对象、Generation、原因和范围下的持续待办不会因轮询、切换当前 Ticket 或文案变化反复发送；解除后再次出现会重新提醒。不同对象不会相互覆盖，完成、主动停止及等待批准分别表达。

人工 `resume` 反馈实际推进结果：Agent 真正开始工作，或 Controller 实际继续检查、合并、收尾；失败或立即出现人工待办时按真实结果提示。收到请求或命令退出 0 不等于恢复成功，不能证明开始时不宣称成功。同一恢复请求本来已在运行时只提示终端；运行中定向恢复 Ticket 仍须等待目标实际执行或新的 PR 状态读取后才报告推进，其他 Ticket 的进展不能替代该结果。同次恢复失败与对应故障去重。自动 Agent 续接和通知发送恢复不属于人工 Resume。无法定位有效 Run 或收件配置的错误仍沿用 CLI 错误边界。

每条消息使用 Card 2.0 compact 私聊卡片。同轮续接不重复启动，重复检查不会刷屏。发布说明已准备、子任务完成和整体交付完成分别表达。

卡片使用蓝色表示开始和进展，绿色表示通过和完成，橙色表示验收未通过后自动修复，黄色表示人工边界，红色表示执行故障。卡片保留明确文字、已有结果摘要与可信耗时；没有摘要时省略摘要；计时缺结束、缺段或关联缺失时明确显示“耗时记录不完整”，可证明的部分累计标为“已记录执行时长”。Agent 结束显示含同轮续接的本轮执行耗时；子任务完成显示子任务累计 Agent 执行耗时；人工待办和最终结果区分累计执行耗时与包含等待的任务历时。补发按业务事件计时，不增加投递等待。按钮仅打开真实 Issue 或 PR，不能执行批准或恢复。

子任务完成表示已经完成并进入集成成果，不是开发或验收 Agent 刚结束。完成卡片保留真实标题、总体进度和下一步，并分别汇总开发（含各类修复）与验收投入：

- 轮数按 Semantic Agent Attempt 身份去重；同轮 Resume、Output Repair、换 Thread 不增加轮数，预算窗口 ordinal 重置也不丢失历史轮数。
- 执行耗时来自关联 Invocation 中已记录的 Worker 执行段，包含同轮续接与 Output Repair，不计凭据准备、Controller 前后置检查、段间检查、暂停、人工或 CI 等待；Invocation 起止时间不能替代段边界。原有累计 Agent 执行耗时仍包含 Publication，不能用开发加验收替代全部总计或任务历时。
- 模型与推理强度来自实际 Invocation 的 Thread Binding。完整且一致时简洁显示，变化或记录部分缺失时按已记录组合展示参与轮数与执行耗时；模型和推理强度单项缺失时仍保留另一项，并标明未记录字段；同轮参与多个组合时明确提示各组轮数不可相加。
- 历史或关联缺失、计时不完整时明确标为“耗时记录不完整”；可靠片段显示“已记录执行时长”，并保留可证明的模型、推理强度及轮次。未知值不补零，不用当前默认或最后配置猜测，不用发现中断时间或后继调用起点补造执行终点。

只统计 Controller 可识别的顶层开发与验收，不推断内部 subagent、Token 或费用。卡片不逐轮列时间表，也不调用模型生成额外摘要；使用卡片中的 `agent-run history <run-id> --details` 查看逐轮配置、耗时及证据。统计复用既有 History，不另存一套累计历史。

Card 2.0 需要支持该格式的飞书客户端；本功能不降级为 Card 1.0。会话摘要与锁屏展示由客户端决定。窄屏单列布局使用飞书内置状态主题，长内容截断并提供本地查询命令。

## 发送记录与恢复

`agent-run status <run-id> --json` 与 `agent-run history <run-id> --json` 的 `notifications` 包含未送达原因与发送记录；普通输出提示不可用或未确认送达数量。两个查询始终只读，不触发发送。

Executor 管理发送线程；外部 CLI 在业务锁外执行。每个事件从进入 outbox 起共用六十秒总期限，最多尝试三次；每次身份预检与发送共用至多十秒，且不能超过事件剩余期限。第一次失败后等一秒，第二次失败后等两秒。发送前持久化次数与所有权，重启、重复观察和并发发送者共用原预算，不能重新计时或重复领取正在发送的事件。

明确失败可以在剩余额度内重试。人工待办、执行故障、更新失败及人工 Resume 失败等重要告警缺少回执时记为 `unknown`，也允许有限重试；当前终态结果沿用这项保护。重试使用同一事件身份派生的幂等键，仍接受少量重复，不能承诺绝对不重不漏。普通进展的 `unknown` 仅记录，不重放。恢复时普通进展只保留模式允许的最新有效状态，压缩不会产生新身份或新预算。已耗尽的同一事件不会因新进展或显式恢复重获额度。

每次领取前回读准确 Run、仓库、Parent、配置与当前对象事实；仍有效的待办保留其 Work Subject、Generation、原因与发生身份。已解除或被新代次替代的待办取消后续投递，保留之前真实结果；解除后再次发生分配新身份，可重新通知。某个对象失败不会重发已送达的其他待办。无法核验当前状态时停止本次发送，不修改业务结果。外部请求已发出后才解除待办，仍可能收到该次消息，但不再重试。

状态回读等通知故障会暂停发送并保留 `unavailable_reason`。后续业务观察或正常退出前回读成功后，由同一发送线程在原调用完成回收后恢复；故障期间不轮询，不重建事件或重置次数、期限。只有发送线程恢复并重新核验状态后才清除故障提示。若退出时仍不可用，未尝试消息记录为 `failed`、零次尝试；已尝试消息保留真实失败或 unknown，另以 `delivery_error` 记录发送工作故障。仍有剩余预算的消息可由健康发送者续接，不会被故障发送者提前删除；原期限或次数耗尽后照常保留耗尽记录。

正常 Executor 退出时，投递收尾最多六十秒，之后取消未结束的调用；transport 最多再用两秒回收线程及 CLI 子进程。退出回执可能因此延后，业务成功、失败或暂停结果不随投递结果改变。短期监督进程会在 Executor 死亡或期限到达时回收 CLI 后代；完全无法执行收尾时的主动退出发现由宿主观察职责承担。没有通知常驻服务，不在退出后无限轮询。

本地记录保存在 Run 状态目录的 `notifications/` 下：待发容量为32条，加固定 Run 对象集合中每个当前边界的一个位置，避免多 Ticket 待办挤掉彼此；日志大小最多1 MiB。最多保留256条最近事件结果，每条至多三次 `attempt_history`，包含次数、开始时间、可证明的结束时间、实际结果、原因及取消标记。没有结束证据的中断仅记录发现时间，不补造发送完成时间。`exhausted` 与 `exhaustion_reason` 区分次数、期限耗尽；`cancelled` 与 `cancel_reason` 标明待办解除、替换或普通过时压缩，原有失败/unknown 结果保留。提交待发或 `sending` 均不表示送达。

去重保留当前有界 history 的身份；首次节点按固定子任务集合保存，人工恢复结果另保留至多256个身份。待办发生序号单调递增，不随近期结果裁剪重置。记录不是完整消息档案。缺少原预算的旧待发记录只保留为 `missing_budget` 耗尽，不分配新额度；新版 Runner 不逐条补发历史进展。查询始终只读，未启用通知不创建 outbox、不启动发送工作。

自动测试使用隔离 CLI 替身，验证发送请求、生命周期与资源回收，不访问真实账号或发送真实聊天消息。
