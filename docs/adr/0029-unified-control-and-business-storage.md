# 执行控制与业务事实同库，保留各自职责

目标架构在每个受管仓库的统一状态目录中，用同一个 SQLite 保存 Task Control 与业务事实。同一次本地迁移涉及的 Action、执行授权、application receipt、Job、Invocation 和预算在一个短事务内核验并提交，减少控制 JSON 与业务数据库先后落盘造成的同步和对账。Task、Action、Executor 和 Job 仍保留独立身份与职责；核心状态按 [ADR 0028](0028-bounded-business-object-persistence.md) 使用明确表与列。

接受控制与业务共享数据库锁竞争和存储故障域的代价。业务保存继续有界协调；生命周期 Action 准入不变成业务保存队列，Stop/Abandon、执行代次和不可取消批准合同继续有效。正常推进与取消、退出、在途结果收口分别核验其权限；Stop 已生效或租约已释放不能阻止准确的退出事实收口，也不能授权新工作。

Host 启停、握手、Agent、Git 和 GitHub 操作仍在事务外；其实际退出证明、未知结果对账和人工显式恢复不能由数据库提交替代。存储失效时保留执行作用域内的取消信号、准确 Worker 进程控制与宿主诊断，不依赖另一笔成功写入才能停止本次执行，不另建可写授权账本。沿用固定受管根及自定义目录只读查询边界。

这是已接受的目标决策，尚未实现。实施必须验证控制响应、跨进程迟到提交、启动和结果落盘崩溃窗口，以及数据库不可用时的真实取消与首次恢复；当前实现合同仍描述原有 Control JSON 与业务 SQLite 边界。
