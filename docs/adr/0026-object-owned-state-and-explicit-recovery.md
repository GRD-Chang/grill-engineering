# 按交付对象保存工作事实，保留退出后的显式恢复

2026-10-15 归档注记：本决策的对象级保存与恢复方向已交付，现行实现合同见[状态存储](../agents/state-storage.md)。后续表示精简与控制同库目标见 [ADR 0028](0028-bounded-business-object-persistence.md)、[ADR 0029](0029-unified-control-and-business-storage.md)，尚未实施。下文保留最初决策时的说明。

本决策已确认，尚未实施；存储引擎见 [ADR 0027](0027-local-sqlite-for-delivery-state.md)，具体提交机制由实现设计确定。日常状态保存按 Delivery Run、Change Job、Semantic Attempt 与 Agent Invocation 的准确归属提交相关变化，避免单票更新重新处理整个 Run 的历史；完整 Run JSON 可作为查询或导出结果。相比继续整体保存后仅改善锁等待，这一取舍使历史增长与日常提交成本分开，并让并行工作的归属直接参与提交判断。

正常的内部提交竞争由程序自动协调，保存成功以持久提交为准。Executor 真正退出后继续等待人工 `resume`，保留原成果、预算、工作身份和已保存结果；不扩大为宿主自动重启或外部副作用重放。Task Control 的执行权威、发布与人工批准、单票故障隔离和未知写入先对账合同继续有效。

故障影响范围决定暂停范围。单对象故障暂停该对象及受依赖影响的工作，独立工作继续；一次保存失败须判断故障归属，不能直接推定整个 Run 无法记录。共享存储持续不可用、整个 Run 已失去可靠记录能力时，关闭全部新工作准入并尽快中断在途工作，即使故障记录本身无法保存也须结束实际执行。此记录故障隔离原则沿用既有整体 Stop/Abandon、共享授权、宿主故障与全局合同门禁，不改变其暂停范围。保留已可靠提交的完成事实和已落盘代码；尚未保存的结果在恢复时核对，不推定成功。显式恢复前须确认原执行已经退出。

新结构只保障按新协议创建的 Run，不兼容或迁移过去的 Run，也不以此次结构调整删除历史成果。既有现场不纳入恢复验收；新 Run 的确定性回归须覆盖并行提交、完成与故障交错、查询重载及公开显式恢复。
