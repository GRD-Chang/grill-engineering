# 按业务变化划分模块，跨业务约束保留共同入口

维护者修改一条交付规则时，应能从对应业务能力找到规则、依赖的事实和行为测试。按通常需要一起修改的代码划分模块。多种交付共用的工作选择、写入授权和事务保证，由单一 Core 的共同入口负责。该决定细化 [ADR 0024](0024-orchestration-responsibility-separation.md)，是后续重构的方向。

以 [Parent 修复 PR](0031-parent-repair-pr-and-repository-ci.md) 为例，修复模块描述候选、目标分支和检查结果满足什么条件才能合入。正式执行合入前，共同授权入口重新核验执行身份和当前状态，并以最新事实调用同一条修复规则。适用规则可以复用，每次获得的授权只适用于当次核验的事实。

一次业务推进涉及的记录、阶段和事件在原事务内一起提交。模块可以接收该事务及完成工作所需的明确输入。物理执行器在事务外交付 Git、GitHub 或进程操作，交回实际结果。这样可以调整内部实现，同时保留并发、重启与未知写入结果下的产品行为。

本轮以实际维护任务比较重构前后的成本。同一条规则需要同步修改的位置减少，或维护者能在模块内完成并验证原本需要跨模块追踪的修改，都可以作为局部代码净增的接受依据。逐批记录生产代码净增减，用于跟踪 [1 万行的长期方向](../architecture-target.md#L95)。
