# 测试指南

## 如何运行测试

1. 使用已安装开发依赖的项目 Python 环境。普通 pytest 已按用例隔离 HOME/XDG，准备工具与 CLI 子进程共用该环境；新增入口也必须保持隔离，不读取或修改真实用户的 Run、Locator 和配置。
2. 本地默认 `make test` 仅运行快速回归；根据受影响的公开行为、共享依赖和已有测试补测相关模块。从具体用例、文件或[模块测试入口](test-commands.md)开始，用 `::用例名` 缩小范围。共享状态、生命周期、持久化、公共接口、测试基础设施或依赖改动，应覆盖直接调用方、同族场景和回归；影响范围不明时扩大验证，必要时全量。
3. 编辑和排障期间运行相关测试。已知修改与相关验证收口后再进入最终验证；临时改完一处不等于最终收口。完整套件失败时，先定向定位、修复，再对修复后的候选完整复验。明确 Finding 或新风险可以要求提前全量。
4. 记录实际命令、结果、验证对象与未覆盖范围。代码、测试、依赖或相关环境变化后重新判断旧结果的适用性，未执行或未完成的检查不得声称通过。

最终验证的责任：

- Development/Repair 不固定每轮全量；稳定候选由独立 Acceptance E2E 完整验证，CI 保留完整套件和必要检查。其他 Reviewer 按风险补充针对性验证，开发自测不能替代独立 Acceptance。
- 普通人工开发在最终交付或合并前也需要完整验证，可采用同一候选的有效 CI 证据，无需固定在本地再跑一遍。需在本地完整验证时运行 `make test-full` 和 `make typecheck`；其余步骤以 [CI workflow](../../.github/workflows/ci.yml) 为准。
- 纯文档、注释等不改变运行行为的修改，检查内容、链接和 diff 即可；可执行示例或行为合同按影响补充验证。

CI 对没有文件变更，或仅修改根目录 Markdown、`docs/` 下 Markdown 或图片的 PR/push，保留必需的 `quality` 检查、记录跳过原因，并跳过依赖安装、测试和类型检查。PR 按相对目标分支的累计差异判断，不只看最后一次提交。`docs/` 下脚本、配置、其他目录的 Skill/Prompt，以及任何混合代码修改仍运行完整 CI。手动触发始终运行完整 CI；无法确定变更范围时也运行完整 CI。图片限 PNG、JPG、JPEG、SVG、GIF、WebP。

同一 PR 更新提交时取消尚未结束的旧 CI；不同 PR、`main` 的 push 和手动运行互不取消。合并到 `main` 后继续检查，并适用相同的轻量或完整验证规则。

## 如何编写和改造测试

- **测试行为**：断言公开接口的结果、错误边界和状态变化，优先扩展现有测试。缺陷修复补充能暴露原缺陷的回归，覆盖直接受影响的同族场景；避免绑定私有函数结构、无关调用次数或重复实现逻辑。
- **分配验证层次**：选择能暴露目标缺陷的最小层级；保留代表性真实 CLI、Git、持久化和进程集成测试，重复纯逻辑组合通过现有模块接口验证。参数化优先扩展轻量逻辑，避免将完整流程乘上大量组合。外部服务使用现有 fake/local 边界；真实 Codex 验证显式 opt-in，不进入普通 pytest 或常规 CI。
- **保留保障**：合并重复测试或调整层次时，说明原有行为、失败边界和历史回归现在由哪里覆盖。测试数量不作为质量门槛；不得删除有效断言、全部换成 mock，或关闭生产持久化、安全检查来提速。
- **隔离状态**：Locator 等可变状态按用例隔离，结果不依赖执行顺序。整次 pytest 的环境隔离不能替代用例隔离；扩大 fixture 生命周期前确认共享内容不会被修改。
- **隔离工具环境**：共享模板和每例都使用测试解释器对应的 PATH，清除继承的 Git 位置与配置覆盖并禁用系统 Git 配置。需要验证配置、PATH 或跨目录行为时，由用例在隔离环境中显式构造；相关入口继续使用真实子进程。
- **控制准备成本**：复用已有准备工具，直接构造合法的最小前置状态；仅在验证前置流程本身时执行该流程。昂贵且不可变的模板可按 worker 复用，每例复制独立可变状态。
- **控制等待成本**：时间和并发测试优先使用可控时钟、事件或同步信号，条件满足即结束等待；保留必要的真实时间与进程边界验证。超时用于有界失败保护，放宽超时或自动重试不能作为提速措施。
- **验证时间与退出边界**：预算测试从窗口创建起使用同一可控时钟，覆盖小数起点、持久化耗时和睡眠越界；控制逻辑使用绝对截止时间，不以整数显示值计时。并发屏障必须有界且失败时释放；清理耗时从准备完成后计起，真实退出断言先于兜底清理。后代进程测试自行回收孤儿，不以 `kill(pid, 0)` 把僵尸误判为活进程。
- **消除偶发失败来源**：先确认子进程或线程已到达目标边界，再触发超时、取消或信号；准备耗时不占用待验证的短时间窗口。构建依赖在[准备步骤](test-commands.md)固定版本与哈希，真实安装测试只使用本地 wheel，继续验证真实构建与安装。疑似偶发失败需定向复现并修复原因，不以自动重试通过作为验收依据。
- **确认模板已静止**：共享模板返回前必须结束所有写入，包括工具启动的后台任务。Git fixture 在初次提交前关闭仓库局部自动维护，副本继承该设置；不得靠忽略复制错误或重试掩盖竞态。这不改变生产仓库配置或持久化行为。
- **并行与清理**：确认隔离后才启用有限并行，控制进程、内存和临时存储开销；成功和失败路径都要退出本例的子进程与线程、关闭 socket，并按[清理规则](test-commands.md)处理临时目录，保留用户状态和其他任务工作区。
- **审查新增成本**：新增重型测试（完整流程、真实子进程或昂贵准备）时，说明保护的风险、轻量测试不足的原因及已有覆盖，记录用例和 setup/teardown 耗时；将执行成本与断言有效性一同审查。

## 优化测试耗时

先测量慢用例及准备成本，再选择改造对象；按相同资源、环境和缓存条件比较，不只展示最快一次。局部反馈包含准备时间，完整 CI 包含依赖安装及全部必要检查，排队和冷启动单列；未达目标时报告差距和瓶颈。

本地完整测试预算为 **300 秒**：开发依赖已安装后的 `make test-full` 命令墙钟，包含准备和清理，依赖安装、类型检查与 CI 单列。比较时固定机器资源、Python 环境和 worker 数，记录命令墙钟、pytest 用时与准备/清理耗时；预算不代表任意机器和负载下的超时保证。保留负载波动余量，约 240 秒可作为优化目标，不是已达成指标。

新增重型测试、修改共享 fixture 或执行策略后，在最终验证中记录修改前后的全量耗时及资源变化，可复用同条件下有效的基线证据，无需每次编辑都跑全量。超过预算或余量明显缩小时，定位最慢用例及 setup/teardown，优先调整验证层级、准备与等待方式；保留有效断言和真实边界保障，明确报告仍未解决的耗时及原因。该预算是审查和验收要求，当前没有自动耗时门禁。

修改测试执行策略、共享 fixture 或重型测试时，遵循本页的五分钟预算、环境隔离、有效覆盖和最终验证要求。涉及 Locator 时，无关失效记录不能阻塞查询；多个匹配候选必须明确消歧，查询不得改写状态。历史讨论为 相关设计记录 和 相关设计记录（私有开发记录，执行本指南不需要访问）。

## 集成测试保留范围

采用 [GitLab 的最低有效层级与分阶段验证原则](https://docs.gitlab.com/development/testing_guide/testing_strategy/)：
本地快速反馈加受影响模块，PR 完整运行现有单元与集成套件。新增加的长流程先明确独有风险；当前不把已有核心回归移到定时任务。

| 核心风险 | 必须保留的真实边界与代表测试 |
| --- | --- |
| 命令入口、暂停与恢复 | `test_cli_mvp.py`、`test_cli_run_supervision.py`、`test_cli_run_repair_supervision.py` 中的真实 run/resume/approve 与进程重新启动 |
| 持久化、授权与版本漂移 | StateStore、Locator、`test_ticket_191_*.py`、`test_git_dispatch_fence.py` 的真实文件、锁、Git 与前后状态断言 |
| Worker 隔离、取消与凭据回收 | `test_codex_backend.py` 的真实子进程、bubblewrap、信号、socket 和清理验证 |
| 安装与离线构建 | 安装器真实构建、激活、回滚及中断恢复；依赖在测试前准备 |

同一流程中的辅助结果查询可以调用进程内公开 CLI；CLI 启动、环境继承、跨目录选择与信号测试仍需真实子进程。
异常分类和纯规则的组合优先在对应模块验证；只有确认每个失败边界已有等效保障，才合并重复长流程，并记录覆盖去向。
